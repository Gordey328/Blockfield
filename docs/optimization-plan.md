# План оптимизации Blockfield

Дата: 2026-10-11, Europe/Moscow. Приоритет — плавность браузерного клиента,
затем загрузка и память, затем подтверждённая ёмкость выделенного сервера.
Начать с воспроизводимых замеров, убрать повторную работу в кадре и сократить
непрерывные операции с чанками. Сложные изменения выбирать по профилю;
проценты ускорения заранее не обещаются.

Исходная точка: HEAD `556c6dce324f1c33817cb182bb50118113195648`;
`game/` совпадает с опубликованным `4c051639e286b3ea4945c77cfa6d568c36bf39be`.
Godot `4.7.2.stable.official.ed1daf0bf`, Compatibility, Web без потоков.
OpenSpades `dcf449c845d509bbde9d79239b32d201c1389961`.
Требования — [iterations](iterations.md) и [parity](parity.md), включая постоянное
повреждение блоков по [ADR0010](decisions/0010-persistent-block-damage.md).

## Существующие оптимизации

Мир уже использует упакованные воксели, отсечение скрытых граней, локальные halo,
индексированные поверхности, объединённые прямоугольники коллайдера и отдельную
инвалидацию столкновений. Main устанавливает карты с отложенной подготовкой
геометрии, воды и изображений карты. Миникарта обновляет общую текстуру по dirty-флагу
с ограничением частоты; большая карта использует ту же текстуру.

Эффекты уже имеют пулы и MultiMesh фрагментов. Сетевая публикация готовит общие
публичные данные один раз, история имеет общий индекс, загрузка сетевой карты
выполняет работу порциями. Сохранить эти механизмы. Пулы звука и падающих кластеров,
а также объединение render faces — самостоятельные следующие кандидаты.

## Приоритеты

Пользователь выбрал пункт4 краткого резюме в чате — звук, VXL и память
(соответствующие части этапов4–5 ниже). Реализация и границы измерений записаны
в [отчёте](optimization-audio-vxl-memory.md) и [ADR0013](decisions/0013-audio-vxl-memory.md).
Подготовка hit volumes и остальные этапы остаются следующими работами.

S — локальная правка; M — несколько связанных модулей; L — изменение алгоритма
или контракта. Это сложность, а не срок. Порядок после этапа 1 уточняется по профилю.

| Этап | Приоритет | Сложность | Результат |
| --- | --- | --- | --- |
| 1. Базовые замеры | P0 | M | Сопоставимые отчёты текущей версии в браузере и на сервере |
| 2. Повторная работа клиента | P1 | S–M | Меньше пересборок UI, поз и копирования неизменного состояния |
| 3. Чанки и окраска | P1 | M–L | Короткие операции при стрельбе и строительстве |
| 4. Звук и попадания | P1/P2 по профилю | M | Меньше лучей, аллокаций и подготовки hit volumes |
| 5. VXL и память | P2 | M–L | Отзывчивая загрузка/сохранение и контролируемая пиковая память |
| 6. Коллапс и стриминг | P2 | M–L | Устойчивость при разрушениях и переходах между чанками |
| 7. История и сервер | P1 для серверной ветки | L | Меньше пиков authority, затем проверка ёмкости |
| 8. GPU и доставка | P2/P3 по профилю | M–L | Проверенные настройки качества и ускорение холодного запуска |

### 1. Получить сопоставимую исходную точку

Сделать отдельный диагностический Web-экспорт с реальным Main и фиксированными
картой, маршрутом, действиями и настройками. Записывать SHA, движок, ОС, CPU/GPU,
браузер, физический размер canvas, DPR, видимость вкладки и прогрев. Один замер
выполнять без других экспортов, движков и тестовых вкладок. Минимум три повтора,
30 секунд прогрева и 120 секунд сценария; отдельно десятиминутная проверка памяти
и нагрева. Нужны настольный браузер и реальный телефон; IAB/эмуляция размеров
экрана дают дополнительную диагностику.

Сценарии: Title.vxl в покое и движение через границы чанков; SMG/Shotgun в стену;
серия гранат и разрушение опоры; 32 видимых актёра; reset/смена карты;
загрузка/сохранение VXL. Сначала профиль 64 м, затем отдельно 128 м и дорогие
опции. Собирать p50/p95/p99/max времени кадра, кадры >50/100 мс, CPU по модулям,
draw calls, объекты/ресурсы, память процесса/доступную память WASM, очереди чанков,
время до первого управляемого кадра и полной подготовки. GPU timer использовать
при доступности; иначе сравнивать разрешения и опции. Этот порядок соответствует
[методике Godot](https://docs.godotengine.org/en/4.7/tutorials/performance/general_optimization.html).

Предлагаемые цели на выбранных устройствах: desktop 60 FPS с p95 кадра ≤16,7 мс;
телефон 30 FPS с p95 ≤33,3 мс, 60 FPS проверять отдельно. Для штатных выстрелов и
одиночных правок стремиться к отсутствию кадров >50 мс. Цели загрузки, максимальных
разрушений и памяти определить после baseline. Это цели работ, а не текущий результат.

### 2. Убрать повторную работу в кадре

- `main.gd:807–821` вычисляет солнечный voxel ray и данные бликов даже при
  выключенном `lens_flare`. Ограничить путь включённой опцией, очистить данные
  при выключении; проверить повторное включение и resource reload.
- `main.gd:173–189` вызывает шесть обновлений позы встроенного персонажа в кадре;
  `character_view.gd:117–181` повторно применяет позу/оттенки. Сделать одно
  обновление встроенной модели и guards неизменных цветов. Сохранить вызовы
  пользовательских skins, анимацию, смерть и режимы камеры.
- `lab_hud.gd:587–629,1127` форматирует HUD, получает статистику и пересобирает
  kill feed. Текст обновлять по изменениям, статистику получать по потребности,
  fade и живые таймеры обновлять независимо. `lab_scoreboard.gd:43` сортировать
  по ревизии списка. Сохранить локализацию, настройки цветов и быстрый feedback.
- `lab_map.gd:163–164` вычисляет видимые цели внутри цикла целей: O(n²) и
  временные массивы на redraw. Вычислить список один раз или использовать тот
  же предикат напрямую, сохранив team/death/spectator правила.
- `Main._poll_network()` обновляет NetworkSession, затем `_process` повторяет
  `session.update(delta)`; poll также вызывается в physics. `network_session.gd:73–152`
  каждый раз глубоко копирует public state и зеркалирует актёров. Разделить
  confirmed metadata по epoch/revision, owner по версии prediction и интерполяцию
  поз на каждый кадр. Сохранить свежую authority перед вводом, event order,
  владение копиями и значимые сигналы `changed`. Polling не убирать без scheduler,
  latency и epoch проверок.

### 3. Сократить непрерывную работу с чанками

`voxel_world.gd:104–113` проверяет бюджет 4 мс после полной перестройки чанка.
`voxel_chunk.gd:34–111` создаёт halo, поверхности и ArrayMesh заново даже при
изменении цвета без изменения топологии. Измерить отдельно подготовку данных,
AO, создание mesh, GPU upload и collider. Сначала исследовать сохранение топологии
и cell→vertices с обновлением цветов; ограничить память дополнительного индекса.

Если геометрия остаётся причиной пиков, разбить подготовку на порции с атомарной
установкой mesh и отменой старого задания по epoch/revision; сначала обрабатывать
работы возле камеры/игрока. Проверять постоянное затемнение RGB, восстановление
только при замене/reset, сохранность collider при косметической правке, AO по
границам/диагоналям и актуальные collision/rays во время подготовки. Принимать
по p95/p99 правок и максимальной непрерывной операции.

### 4. Проверить звук и подготовку попаданий

`openspades_audio.gd:86–97` выполняет 24–48 лучей на `compute_ambience`, который
вызывает каждый shot (`openspades_audio.gd:127`). Они не входят в существующий
лимит room/obstruction 128 лучей/1,5 мс. Добавить полный счётчик. Затем проверить
bounded cache точного eye + Data identity/epoch/map_sequence, с инвалидацией
на reset/замене; при движении выигрыш может быть мал. Не приближать окклюзию.

При заметной стоимости audio nodes (`openspades_audio.gd:224,280`) проверить
bounded pool: сохранить dry/wet routes, синхронный STREAM, pitch/gain и отсутствие
хвостов при reset. Применить PCM/environment/Web audio проверки и прослушивание.

Offline Shotgun повторно готовит hit volumes каждой цели для каждого pellet
(`player_controller.gd:761,813`, `lab_hit_volumes.gd:86–90`). Готовить геометрию
раз на выстрел, сохранив RNG, tie/range и последовательные damage/alive проверки.
Для hottracking (`hottracked_player.gd:81–111`) проверить cache точной позы,
hit parts и team color с инвалидацией при resource reload, а также reuse буферов
линий; скрытые имена не должны отключать исходный контур цели.

### 5. Сделать VXL и память управляемыми

Сохранить порционную визуальную подготовку. Локальные decode/encode VXL
(`vxl_reader.gd:10–59,65–111`) остаются синхронными. Сделать задания по колонкам
с прогрессом и отменой. Decode строит частные данные и атомарно устанавливает
карту после полной проверки. Save представляет одну целостную версию при
одновременных правках; snapshot/COW или короткий барьер выбрать по замерам и ADR.

Измерить пики при join/decode/reset/save/resource reload: Data, frozen copy,
staging, история, mesh, изображения, временные буферы. Проверить 20 циклов и
плато после освобождения. Проверить `_material_cache` при произвольных RGB
(`openspades_models.gd:12,88–93`); bounded eviction вводить при подтверждённом
накоплении с сохранением точных цветов. Проверки VXL: occupancy, solid black,
exposed colors, нижние слои, повреждённые файлы, epoch cancellation и отсутствие
частично принятой карты. Потоки/GDExtension не являются исходным решением Web.

### 6. Стабилизировать коллапс и стриминг

`voxel_data.gd:411–450` выполняет синхронный DFS с Vector3i/Dictionaries. Измерить
visited cells/time большой неподдерживаемой конструкции. Первый кандидат —
линейные индексы, reuse packed stack и visited bitset/stamps. Поддерживаемые связи
изучать при оставшемся bottleneck. Сохранить атомарную authority транзакцию,
детерминированные collapse groups, опору на два нижних слоя и сохранение
импортированных плавающих компонентов до затрагивающего их удаления;
частичный мир не публиковать.

`falling_cluster.gd:53–97,116–178,230–249` создаёт mesh/material/MultiMesh отдельно
и обновляет инстансы по одному. Лимиты 24 ×4096 fragments/1024 smoke допускают
теоретически 98 304/24 576 инстансов. После stress-замера проверить пулы ресурсов
и bulk buffer upload. Глобальная выборка/бюджет меняют представление: отдельный
ADR, явный уровень качества и визуальное сравнение; малые кластеры сохраняют counts.

`voxel_world.gd:535–554` сразу удаляет дальние чанки на границе стриминга.
Проверить occupancy summaries пустых чанков, очередь по близости и узкий retention
margin с лимитом памяти. Проверки: новые блоки в пустых чанках, collider рядом с
игроком, возврат повреждений после unload/reload, отмена старых заданий при reset.

### 7. Уменьшить пики сервера и подтвердить ёмкость

`hit_history.gd:168–246` повторно проверяет retained receipts и инвалидирует
terrain index каждый кадр. Historical stress 32 768 изменений: apply 266–277 мс,
history record 199–210 мс, cold index 48–50 мс. Исследовать инкрементальную
валидацию before/after и generations, затем reuse immutable index с ограниченными
памятью/leases. Сохранить отзыв queries, life/color guards, закрытые кадры,
missing-history denial; частичную authority не разносить по тикам.

По профилю заменить reflection copy явным typed copy, выделить common validators
вместо encode ради проверки (`simulation_codec.gd:278`, `events_codec.gd:412`),
исследовать public wire capture вместо полного private snapshot. Сохранить
hostile-packet rejection, byte goldens, privacy. Общая публикация и hit volumes
раз на shot уже существуют; дальнейший reuse требует проверки leases.

Затем Linux release server отдельно от клиентов: 1/8/16/32 игроков, paced 60 Гц,
публикация 20 Гц, Title, sustained fire/reload, одновременные join, гранаты/правки,
TCP stalls. Измерять весь цикл poll+authority+history+publication, tick lateness,
catch-up, snapshot age, bandwidth/queues. Цель: p95 полного цикла ≤16,667 мс без
нарастающего отставания за 10 минут. Отдельные p95 подсистем не складывать как
измеренный общий p95. Поддерживаемый roster следует из этого теста.

### 8. Оптимизировать GPU и холодный запуск по профилю

Сравнить один кадр при разных физических разрешениях, shadows/smoke/HDR/bloom/
GI/reflections. Draw calls не отражают всю стоимость прозрачных пикселей;
учитывать [особенности GPU и WebGL](https://docs.godotengine.org/en/4.7/tutorials/performance/gpu_optimization.html).
GI/reflections/HDR уже выключены по умолчанию. При GPU-пределе проверить доступный
в Compatibility масштаб 3D отдельно от UI, shadow sizes и частоту дополнительных
viewport. Изменения качества — понятные настройки с проверкой на телефоне.

Greedy render meshing изучать позже с сохранением RGB/damage/AO atlas/seams;
greedy collider уже есть. MultiMesh группировать пространственно: отдельные
инстансы не имеют собственного frustum culling ([Godot](https://docs.godotengine.org/en/stable/tutorials/performance/using_multimesh.html)).

Для доставки записать cold/warm HTTP transfer/cache, WASM compilation, импорт и
prewarm. Проверить состав PCK и зависимости локализации/overrides; удалять только
доказанно ненужные ресурсы. Кастомный движок, другой renderer и threaded Web
рассматривать отдельно лишь при подтверждённом пределе более простых мер.

## Организация и критерии приёмки

Будущая команда: мир — `world/` и world tests; презентация — `presentation/`,
`audio/`, `ui/` и tests; сеть — `simulation/`, `network/` и tests. Координатор —
Main/Controller, общие контракты, project/export config, диагностика, docs и
публикация. До правок согласовать revision tokens, задания чанков и метрики;
пересекающиеся файлы передавать явно. Это план, текущих редакторских leases нет.

Изменение принимать по снижению целевой стоимости сверх разброса повторов,
без регрессии поведения/неприемлемого роста памяти. После правки — parser/import
и affected behavioral checks; после этапа — native benchmark и реальный Web-экспорт
с интерактивной/визуальной проверкой. Перед публикацией — полный frozen release
checkpoint и опубликованные hashes. Тяжёлый performance stress держать opt-in,
короткие проверки корректности — в CI. ADR фиксирует выбранное изменение контракта.

Существующие команды для будущих замеров, запускать последовательно в окно движка:

```powershell
& .tools/godot/Godot_v4.7.2-stable_win64_console.exe --headless --path game --script ../tests/world/benchmark_world.gd
& .tools/godot/Godot_v4.7.2-stable_win64_console.exe --headless --path game --script ../tests/network/benchmark_server_capacity.gd -- --publication=prepared --output-name=optimization-server-baseline.json
& .tools/godot/Godot_v4.7.2-stable_win64_console.exe --headless --path game --script ../tests/network/benchmark_server_capacity.gd -- --sockets-only --socket-clients=32 --output-name=optimization-sockets-baseline.json
```

World benchmark включает синхронные диагностические пути и не заменяет Main с
deferred visuals. Server fixture не заменяет раздельные процессы и paced Linux
acceptance. Полный release: `tools/release_checkpoint.py --revision <commit> --server`
через Python из [status](status.md). Новые browser scenarios и paced server harness
входят в этап 1. В этом планировании новые показатели производительности не измерялись.
